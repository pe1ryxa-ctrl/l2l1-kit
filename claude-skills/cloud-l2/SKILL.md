# cloud-l2 — дві сесії L2: основна ↔ хмара

Протокол — розділ «Друга сесія L2 у хмарі» в `CLAUDE.md` (kit). Тут — як це робити руками й без помилок.

## Хто що бере
| Хмара (працює на Cloud session credits, не на ліміти плану) | Основна (машина власника) |
|---|---|
| рецензії й вердикти (субагенти, повні прогони на Linux) | HIL, залізо, стенди, SSH на пристрої |
| злиття гілок `fallback/*` після VERIFIED, контрольні прогони | скрипти деплою для власника (VPS, РМ) |
| постановка task-файлів, хмарні виконавці (routine / фолбек) | локальні дерева L1: незакомічене, незавершені злиття, stash |
| дослідження, аудити | усе, що бачить лише машина власника |

Важке — у хмару. Хмара не бачить файлової системи машини; основна не бачить транскрипту хмари.

## Канал
- **Основна → хмара:** `SendMessage` до хмарної сесії (ім'я — з `ListAgents`, рядок `· cloud`) — **односпрямовано**, підтвердження не приходить; **плюс** запис у файл (для всього, що довше двох рядків, і для кожного рішення власника).
- **Хмара → основна:** лише запис у `docs/HANDOFF-cloud.md` (прямого шляху назад немає).
- **Пуші хмари в основні гілки** авторежим хмарної сесії може зупинити — власник підтверджує у **її** чаті, навіть якщо вже сказав «так» основній сесії. Нагадуй про це власнику.

## Скрипт `handoff.py` (поруч із цим файлом; лише stdlib)
Запускати з будь-якого місця всередині meta-репозиторію. Сам робить `pull --ff-only`, правку, коміт **лише цього файла**, `push`; якщо інша сторона встигла запушити — повторює на свіжому файлі (до 5 разів).
```bash
python .claude/skills/cloud-l2/handoff.py add --side main --title "KWS-028 — доробка хмарі" --body-file note.md
python .claude/skills/cloud-l2/handoff.py owner "KWS-028" "**хмара**"          # власник рядка таблиці (збіг має бути одним)
python .claude/skills/cloud-l2/handoff.py owner --add "KSIM-010 HIL" "основний"
python .claude/skills/cloud-l2/handoff.py latest --side cloud -n 2              # останні записи іншої сторони
python .claude/skills/cloud-l2/handoff.py watch --side cloud --interval 180 --max 60   # у фоні
```
`--side` — хто пише (`main` = основна, `cloud` = хмара); для `latest`/`watch` — чиї записи дивитись. `watch` спершу перевіряє, що бачить origin (інакше exit 2 — сторож, що нічого не бачить, гірший за відсутній), і виходить із кодом 0 на першому новому записі — запускати у фоні й читати, коли розбудить.

## Запис-передача — що в ньому має бути
1. **ID і дія** (рецензія / злиття / постановка / виконавець / HIL) і хто власник після передачі (рядок таблиці).
2. **Живі факти:** хеші комітів і гілок, `status` у task-файлі, конфігурація заліза/мережі, числа прогонів — з командою, а не з пам'яті.
3. **Межі:** які шляхи не чіпати (там L1 або інша сесія) і що вимагає згоди власника.
4. **Критерій готовності** і куди звітувати (запис у файл; вердикт — у кінець task-файла).
5. **Рішення власника**, отримані однією сесією, — дослівно, як остаточні.

## Правила (уроки Kambala 2026-09-29)
- **L1 отримує `/task` лише для файла задачі, що вже є на origin.** Чернетка в записці — не задача: L1 без файла сам почав зливати чужу гілку.
- **Гілки `fallback/*` зливає лише Архітектор** (будь-яка з двох сесій — за таблицею), після VERIFIED.
- **Одна робота — один власник** у таблиці; перед правкою task-файла чи гілки — `handoff.py latest` і таблиця.
- **Незавершений стан на машині** (злиття, stash, WIP L1) хмара не бачить — основна описує його в записі, якщо він важливий.
- **Сторож обов'язковий**, коли чекаєш на іншу сесію: власник не повинен бути тим, хто каже «хмара вже відпрацювала».
- **Повторив алгоритм двічі — запропонуй скіл** (цей скіл з'явився саме так).
