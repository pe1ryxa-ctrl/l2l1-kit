# cloud-oneoff — разовий хмарний виконавець від запуску до `done`

Протокол — «Хмарний фолбек» і «Нічна хмарна черга» в `CLAUDE.md` (kit). Тут — механіка, яку інакше щоразу збирають руками (урок DDL 29.09: десять ручних запусків за ніч, два падіння сторожа й одна хибна тривога перед злиттям).

Скрипт `oneoff.py` поруч (лише stdlib). Шлях після `sync.py`: `.claude/skills/cloud-oneoff/oneoff.py` у корені meta-репозиторію.

## 1. Запуск
1. **Перевірки до запуску.**
   - ТЗ погоджене (5.1).
   - Гілки `fallback/<id>` ще немає: `git ls-remote --heads origin fallback/<id>`.
   - До найближчого запуску нічної routine за розкладом **понад 10 хв**.
   - Паралельні задачі не правлять ті самі файли коду.
2. **Тіло запиту:**
   ```bash
   python .claude/skills/cloud-oneoff/oneoff.py body --id DAI-077 --project DAI \
     --about "Python knowledge-base pipeline plus a Ukrainian chat bot" \
     --repo-url https://github.com/<owner>/<repo> --env-id <env_…> \
     --forbid "src/x.py (local DAI-061), scripts/y.py (DAI-052)"   # або --forbid none
   ```
   - **`--forbid` обов'язковий** (протокол): зайняті шляхи через кому або явно `--forbid none`.
   - `--env-id` — з наявної routine: `RemoteTrigger get` → `job_config.ccr.environment_id`.
   - `--test-cmd` і `--setup` — точна команда набору й середовище проєкту (дефолт — Python/pytest DAI). Від них залежить, чи порівнюються однакові множини «до/після».
   - Для доробки на наявній гілці: `--iteration N` (N ≥ 2). Спершу вердикт на доробку записується в кінець task-файла **на гілці**, `status: pending`, коміт і push. Конфлікт коду при злитті `main` виконавець не розв'язує сам: `merge --abort` і опис у звіті.
   - Додаткові обов'язкові вказівки — через `--extra "…"` (вставляються перед кроком звіту). Щоб побачити лише текст: `--prompt-only`.
3. `RemoteTrigger` `action: create`, `body` — **виведений JSON без змін**. Тіло передається інлайн у виклику інструмента, прочитай вивід і встав.
4. Власникові — ID routine й час запуску (вони є в результаті).

## 2. Сторож (у фоні, `run_in_background`)
```bash
python .claude/skills/cloud-oneoff/oneoff.py watch --repo <P> --branch fallback/dai-077 \
  --task .agents/tasks/DAI-077.md [--require "## Ітерація 2"]
```
- Спершу **самоперевірка тим самим механізмом, що й цикл**: `ls-remote` бачить `main` (або `--self-check <наявна гілка>`), і `fetch` його справді доставляє. Збій мережі на старті — до `--start-retries` спроб (дефолт 3), потім exit 2 `SELF-CHECK FAILED`. Гілки `main` на origin немає — exit 2 одразу, без повторів (урок Kambala 28.09).
- **На старті сторож оцінює й поточну голову гілки.** Якщо звіт уже там (`status: reported` і `--require`, якщо задано) — друкує `ALREADY REPORTED <sha> …` і виходить з 0, як після звичайного REPORTED. Інакше спрацьовує на **новому** коміті після старту з тими самими умовами. Урок DDL 30.09: звіт з'явився до старту сторожа, і той ~2 год чекав коміту, якого вже не буде.
- **Для ітерації N ≥ 2 `--require "## Ітерація N"` обов'язковий.** Без нього звіт ітерації 1 на гілці дасть хибний `ALREADY REPORTED`, якщо коміт вердикту зі `status: pending` ще не запушено.
- **Збої мережі в циклі не вбивають сторожа.** Невдалі `ls-remote`/`fetch` (напр. DNS `Could not resolve host`, двічі за 30.09) друкуються як `transient failure k/K` і повторюються на наступному опитуванні. Exit 2 `BLIND` — лише після `--max-failures` збоїв поспіль (дефолт 10, тобто ~20 хв при `--interval 120`). Успішне опитування скидає лічильник.
- Гілка читається за sha з `ls-remote` через власний ref `refs/oneoff-watch/<гілка>`, не через спільний `FETCH_HEAD`. Тому паралельні сторожі й ручний `git pull` одне одному не заважають.
- `--heartbeat N` друкує «still waiting» кожні N опитувань. Тести сторожа: `python -m pytest -q -p no:cacheprovider claude-skills/cloud-oneoff/tests` (у kit; локальний bare-репозиторій, без мережі).
- **Один сторож — одна гілка.** Bash-інструмент на macOS — zsh: `${!var}`, асоціативні масиви bash і `eval`-трюки там ламаються (урок DDL 30.09).

## 3. Рев'ю
Незалежний субагент лише на читання, з живими фактами в промпті (протокол 5.4). Повторне рев'ю ітерації N краще давати **тому самому** рецензентові (`SendMessage`): він уже має контекст і власні скрипти.

## 4. Злиття
0. **Задача з `hil_required: true` не зливається до письмового HIL PASS власника** (протокол 5.4, урок DAI-047): інакше вотчдог чи збій перезапустить сервіс, і неперевірена поведінка ввімкнеться сама.
1. **Конвеєр не працює саме з робочого дерева.** Перевірка йде за **cwd процесу**, а не за назвою. Тести рецензентів запускають справжні `update_*.sh` у тимчасових копіях (хибна тривога DDL 29.09):
   ```bash
   python .claude/skills/cloud-oneoff/oneoff.py idle --repo <P> \
     --proc "update_only.sh|update_knowledge_full.sh|rag_scraper.py" --lock /tmp/dai_update.lock
   ```
   - Exit 0 IDLE, 1 BUSY, 3 UNKNOWN. **Зливати лише при 0**: bash читає скрипт по ходу виконання, і заміна `.sh` посеред прогону зсуває його.
   - UNKNOWN — не вдалося прочитати `ps` чи cwd процесу, або це Windows/Git Bash. Перевір руками.
   - BUSY — cwd процесу всередині репозиторію або шлях репозиторію є в його командному рядку.
2. `git pull --ff-only`, потім `git merge --no-ff --no-commit origin/fallback/<id>`.
3. Конфлікт лише в Changelog: `oneoff.py changelog <P>/Changelog_X.md`, потім `git add` цього файла.
   - Лишає обидва записи, гілка зверху; розуміє стиль `diff3`.
   - Відмовляє, якщо конфліктних блоків не рівно один або маркери лишились. Конфлікт у коді — руками.
4. Коміт злиття: `Merge fallback/<id>: … [L2 fallback]`.
5. **Контрольний прогін з чистої копії коміту злиття** (`git archive <hash>`, протокол 5.4) на машині Архітектора. Множина падінь — не більша, ніж на `main`.
6. Вердикт — у кінець task-файла, `# Verdict — VERIFIED (<date>, Архітектор)`: підсумок рецензента, прийняті зміни поза ТЗ, неблокуюче.
7. Закриття:
   ```bash
   python .claude/skills/cloud-oneoff/oneoff.py close --repo <P> --id DAI-077 --merge <hash> [--push]
   ```
   Заголовок вердикту мусить містити слово «Verdict» (`# Verdict — VERIFIED (…)` або `## Verdict ітерації N — …`). Старий формат `## Ітерація N — VERIFIED` скрипт не визнає.

   Скрипт відмовиться, якщо:
   - останній заголовок `# Verdict` / `## Verdict` не VERIFIED (у заголовку чи першому рядку після нього), він негативний (REJECTED, «доробк…», «не VERIFIED») або після нього є розділ ітерації чи звіту;
   - `hil_required: true`, а `--hil-pass` не передано. **З HIL не зливати до письмового PASS власника** (протокол 5.4, урок DAI-047);
   - йде злиття (MERGE_HEAD), HEAD не на `--main` або в індексі є чужі staged-зміни.

   Далі він:
   - ставить `status: done`;
   - виконує `git add`, **потім** `git mv` у `tasks/done/` (урок DDL 28.09);
   - позначає `[x]` у `cloud_queue.md`;
   - робить коміт **лише цих шляхів**.

   `--push`: якщо в `.github/workflows` є тригер `push`, скрипт відмовиться пушити, бо push може бути деплоєм (протокол §6). Перевір `paths-ignore` і запуш сам або передай `--push-is-not-deploy`.
8. Наступну задачу черги — одразу разовим запуском, не чекаючи розкладу.

## Застереження
- Хмарний виконавець працює на Linux. Тести з парами шляхів, що різняться лише регістром, падають на macOS і Windows (урок DDL 30.09, DAI-076). Прогони з чистої копії на машині Архітектора обов'язкові.
- Числа «до/після» з хмари можуть відрізнятися на 1–2 тести через середовище (root, мережа). Порівнювати **множини** падінь з чистих копій на своїй машині.
