## Протокол задач
1. Старт — тільки `/task <ID>` (`.agents/workflows/task.md`). Один файл = одна задача; наступну не починай, поки поточна не `reported`.
2. Критично прочитай ТЗ і `[SSOT Context]`. Дірка в ТЗ — виправ, якщо очевидно, або зупинись і опиши в Report.
3. Глибокий аудит дотичного коду → реалізація → самоперевірка (лінтери, build, тести) → автономне виправлення до зеленого.
4. SSOT: `Context_{{X}}.md` (якщо зачеплено архітектуру) → запис у `Changelog_{{X}}.md` → ВИДАЛИТИ виконаний пункт із `Plan_{{X}}.md` (Plan = лише беклог) → `USER_GUIDE.md`, якщо змінилась поведінка для користувача.
5. `git status --short` → прибрати свої scratch-файли → `git commit` + `git push` (task-файл комітиться разом із кодом; якщо remote ще немає — лише commit).
6. Заповнити `# Report` (Що зроблено · Верифікація · **Errors & Obstacles** — завжди · SSOT-чекбокси · хеш коміту) → `status: reported` → коміт `docs(task): report <ID>`.
7. Статуси `verified` / `done` ставить лише Архітектор.

## Errors & Obstacles
Обов'язковий розділ Report, навіть якщо все пройшло гладко. Фіксуй помилки компіляції, логічні баги, системні проблеми та рішення — з цього Архітектор синтезує нові правила і скіли.

## Субагенти
Дозволені **лише read-only**: дослідження коду/документації (великі `Context_*`/`Changelog_*`, огляд модулів), незалежне рев'ю перед Report, аналіз великого виводу тестів. Субагент НЕ редагує файли і НЕ виконує команд, що змінюють стан. В одній задачі один письменник — ти. Не більше 2 субагентів на задачу, якщо в ТЗ (поле `subagents:`) не сказано інакше. Результат субагента — стисла вижимка; у Report зазнач, що делегувалось. Для задач із кодом рекомендований рев'ю-субагент перед Report із чек-листом: Definition of Done, boundary, SSOT, залишки scratch-файлів. Build і тести запускаєш ти сам — це не делегується. Антигравіті-артефакти (task list, implementation plan, walkthrough) не замінюють Report у task-файлі.
