## Протокол задач
1. Старт — тільки `/task <ID>` (`.agents/workflows/task.md`). Один файл = одна задача; наступну не починай, поки поточна не `reported`.
2. Критично прочитай ТЗ і `[SSOT Context]`. Дірка в ТЗ — виправ, якщо очевидно, або зупинись і опиши в Report. План реалізації на погодження Архітекторові не надсилається: ТЗ уже схвалене, гейт один — Report і `git diff`. Заперечення й питання — у `Errors & Obstacles` + `status: reported`, не в чат.
3. Глибокий аудит дотичного коду → реалізація → самоперевірка (лінтери, build, тести) → автономне виправлення до зеленого. Скрипт, який ти створив, має бути розпарсений або запущений до Report — вивід у розділ «Верифікація». Скрипт, перевірений лише читанням, вважається неперевіреним.
4. SSOT: `Context_{{X}}.md` (якщо зачеплено архітектуру) → запис у `Changelog_{{X}}.md` → ВИДАЛИТИ виконаний пункт із `Plan_{{X}}.md` (Plan = лише беклог) → `USER_GUIDE.md`, якщо змінилась поведінка для користувача.
5. `git status --short` → прибрати свої scratch-файли → `git commit` + `git push` (task-файл комітиться разом із кодом; якщо remote ще немає — лише commit).
6. Заповнити `# Report` (Що зроблено · Верифікація · **Errors & Obstacles** — завжди · SSOT-чекбокси · хеш коміту) → `status: reported` → коміт `docs(task): report <ID>`.
7. Статуси `verified` / `done` ставить лише Архітектор.

## Errors & Obstacles
Обов'язковий розділ Report, навіть якщо все пройшло гладко. Фіксуй помилки компіляції, логічні баги, системні проблеми та рішення — з цього Архітектор синтезує нові правила і скіли.

## Заміри · Тести · Порядок перевірок
- **Замір — по коду, що перевіряється.** Бенчмарк, латентність чи прогін тестів у Report вказують, **який процес і який коміт** заміряно. Після зміни коду сервіс перезапускається або прогін іде in-process; замір проти старого процесу недійсний і не приймається.
- **Наявні тести — контракт.** Послабити перевірку (`==` → `in`), пропустити (`skip`/`xfail`) чи видалити її можна лише з письмовим обґрунтуванням у Report, чому вимога більше не діє. Тест, що «позеленів» через послаблення, = REJECTED. Перед Report зелений **увесь** набір, включно зі старими тестами.
- **Дешеві гейти — перед дорогими.** Порядок: компіляція/лінт → юніт-тести → короткий сценарій → повний прогін. Провалено дешевий гейт — дорогий не запускати, а звітувати провал.

## Субагенти
Дозволені **лише read-only**: дослідження коду/документації (великі `Context_*`/`Changelog_*`, огляд модулів), незалежне рев'ю перед Report, аналіз великого виводу тестів. Субагент НЕ редагує файли і НЕ виконує команд, що змінюють стан. В одній задачі один письменник — ти. Кількість субагентів не обмежена — запускай їх щоразу, коли це пришвидшує роботу або підвищує якість (паралельне дослідження, незалежне рев'ю); поле `subagents:` у ТЗ задає мінімум очікуваного, не максимум. Результат субагента — стисла вижимка; у Report зазнач, що делегувалось. Для задач із кодом рекомендований рев'ю-субагент перед Report із чек-листом: Definition of Done, boundary, SSOT, залишки scratch-файлів. Build і тести запускаєш ти сам — це не делегується. Рев'ю-субагент має **перевіряти**, а не підтверджувати: у вижимці — конкретні виконані перевірки з виводом; «усе відповідає DoD» без доказів не є рев'ю. Підсумок «виправлено» в Report ставиться після перевірки, не замість неї. Антигравіті-артефакти (task list, implementation plan, walkthrough) не замінюють Report у task-файлі.

## ADLP · Scratch · Деплої
Деструктивні дії (rm, DROP, docker down -v, erase-flash, git reset --hard, force-push, будь-що на віддалених машинах) — лише після явної згоди користувача через `ask_question`.
Видалення файлів даних чи записів — деструктивна дія незалежно від того, як названо крок: «злиття», «дедуплікація», «консолідація», «очищення» винятками не є. Понад поодинокі файли — тільки після `ask_question`, навіть якщо цей крок прямо описаний у ТЗ; у Report — точна кількість, перелік і шлях до бекапу. Дані поза git відновити нізвідки: перед таким кроком бекап обов'язковий, і він живе не в scratch-директорії. Тимчасові файли — тільки в scratch-директорії Antigravity, не в репозиторії. Деплої на віддалені цілі (VPS, пристрої) — лише за прямою командою користувача.
