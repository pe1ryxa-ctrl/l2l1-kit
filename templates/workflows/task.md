# /task <ID>

Ти — L1 Developer цього проєкту. Архітектор (Claude, L2) поклав задачу у файл `.agents/tasks/<ID>.md`.

## Steps

1. **Знайти файл.** Аргумент після `/task` — ID (наприклад `STC-017`). Відкрий `.agents/tasks/<ID>.md`. Якщо ID не передано — знайди в `.agents/tasks/` файли зі `status: pending`; якщо їх кілька — запитай користувача, який брати.
2. **FATAL BOUNDARY CHECK.** Виконай `pwd` і звір з полем `workspace` у файлі. Не збігається — зупинись із `FATAL ERROR: wrong workspace`.
3. **Статус.** Зміни `status: pending` → `status: in_progress`.
4. **Прочитай SSOT.** Відкрий `[SSOT Context]` і відповідні розділи `Context_*.md` та `Plan_*.md`. Прочитай `.agents/AGENTS.md`, якщо ще не читав у цій сесії.
5. **Критично прочитай ТЗ.** Якщо бачиш логічну дірку, відсутню залежність або суперечність із кодом — виправ, якщо очевидно; інакше зупинись і опиши проблему в `# Report → Errors & Obstacles`, постав `status: reported` і завершуй.
6. **Виконай.** Глибокий аудит дотичного коду → реалізація → самоперевірка (лінтери, build, тести — усе, що вказано в Definition of Done). Помилки виправляй автономно до зеленого результату.
   План реалізації Архітектору **не надсилається і не узгоджується**. Схвалення плану в цьому протоколі не існує: ТЗ уже схвалене Gans, а єдиний гейт — Report і `git diff` після роботи. Внутрішній план Antigravity — твій робочий інструмент, не канал комунікації.
7. **SSOT.** Онови `Context_*.md` (якщо зачеплено архітектуру), додай запис у `Changelog_*.md`, ВИДАЛИ виконаний пункт із `Plan_*.md`. Онови `USER_GUIDE.md`, якщо змінилась поведінка для користувача.
8. **Чистота.** `git status --short` → прибери свої scratch-файли. Не чіпай чужих незакомічених файлів. Файли — лише з LF (без попереджень про CRLF у `git diff`). Якщо квота закінчується — WIP-коміт (`wip(<ID>)`) і підрозділ «Стан на момент зупинки» у Report, статус `in_progress`.
9. **Commit & push.** **Код і звіт — різними комітами** з правдивими повідомленнями: код — `feat|fix(...)`, звіт — `docs(task): report <ID>`; код під повідомленням `docs(...)` — помилка. **Комітити лише свої файли поіменно** (`git add <шлях> …`), ніколи `git add -A`/`git commit -a`: у воркспейсі може працювати інший виконавець. Перед `push` — `git pull --rebase`.
10. **Мутаційна перевірка** (обовʼязкова при `hil_required: true` і для змін, від яких залежить безпека, відновлення після збою або цілісність даних). Навмисно зламай найважливіші гілки своєї роботи — по одній — і переконайся, що тести падають, і саме ті, що мають. У Report — таблиця, де для **кожної** мутації: точна правка (файл, рядок, було → стало), команда запуску і **вивід тесту, що впав**. Рядок «KILLED» без виводу не приймається: у Kambala 2026-09-24 таблиця заявила вбиту мутацію, яка насправді вижила. Мутація, яка **вижила**, означає, що тест не перевіряє поведінку: або виправ тест, або напиши прямо, що гілка не покрита. Не ховай цього.
11. **Report.** Цифри тестів, лінтера і будь-які заміри — **з чистої копії коміту** (`git archive <хеш> | tar -x -C <тимчасовий каталог>`, свій `PYTHONPATH`), а не з робочого дерева. Заповни всі підрозділи `# Report` у task-файлі (включно з Errors & Obstacles, таблицею мутацій і хешем коміту), постав `status: reported`, закоміть і запуш ще раз (`docs(task): report <ID>`). **Не пиши у Report вердиктів** («PASS», «VERIFIED», «готово до продакшену») — рішення про готовність виносить Архітектор; твоя частина — факти й докази.
12. **Завершення.** Повідом користувача одним рядком: `<ID> reported — <hash>`. Не починай іншу задачу.

## Заборонено
- Надсилати Архітекторові план реалізації на погодження або чекати від нього «ок» посеред задачі. Питання й заперечення йдуть **у файл**: `# Report → Errors & Obstacles` + `status: reported`. Чат — не канал L1→L2; усе, чого немає в task-файлі, для Архітектора не існує.
- Виконувати задачу з іншого проєкту або змінювати файли поза воркспейсом.
- Ставити `status: verified` чи `done` — це робить лише Архітектор.
- Деплоїти на віддалені цілі (VPS, пристрої, prod), прошивати/стирати пристрої, робити `git reset --hard`, видаляти дані без явної згоди користувача (ADLP).
