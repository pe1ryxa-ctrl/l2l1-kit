## 3. Бутстрап кожної сесії (обов'язково, до будь-якого ТЗ)

1. Підключити папку `{{ROOT}}` (за потреби — `{{GEMINI_CONFIG}}`).
2. Прочитати `Global_Context.md` → `Global_Roadmap.md`.
3. Для підпроєкту, про який мова: `Plan_<X>.md`, релевантні розділи `Context_<X>.md` (grep за розділами, не весь файл).
4. Перевірити `<P>/.agents/tasks/*.md` зі `status: reported` — верифікувати ПЕРШИМИ.
5. Перевірити `git -C <P> status --short` — незакомічені хвости від L1 = червоний прапорець.

Між сесіями оперативний контекст втрачається. SSOT + task-файли — єдиний «жорсткий диск». Чого немає в них — того не існує.

## 4. Права на запис

**Можна:** `Global_*.md`, `CLAUDE.md`, `.agents/*` кореня, `<P>/.agents/**` (AGENTS.md, rules, skills, workflows, **tasks**), `{{GEMINI_CONFIG}}/**` (з коротким повідомленням Gans про кожну зміну), коміти в meta-репозиторії кореня.
**Не можна:** код підпроєктів; Holy Trinity підпроєктів (`Context_X/Plan_X/Changelog_X` — зона L1; при деградації — задача L1 на рефакторинг SSOT); `git commit/push` у воркспейсах L1 (крім `.agents/` за явною згодою); деплої, прошивки, будь-які ADLP-дії.

## 5. Цикл задачі

```
Draft ──(показати Gans)──▶ pending ──(/task ID у Antigravity)──▶ in_progress ──▶ reported
   ▲                                                                                 │
   └──── rejected ◀──────────── верифікація Claude ◀─────────────────────────────────┘
                                       │
                                       ▼ verified ──(HIL PASS, якщо hil_required)──▶ done
```

**5.1 Draft.** Перед записом файлу показати Gans пояснення (2–4 речення): що, навіщо, в який підпроєкт, ризики. Файл пишеться лише після його «ок». Стосується КОЖНОГО ТЗ.
**5.2 Файл задачі.** Шаблон — `.agents/TASK_TEMPLATE.md`. Шлях: `<P>/.agents/tasks/<TAG>-<NNN>.md`; номер = максимальний у `tasks/` та `tasks/done/` + 1. Обов'язково: frontmatter, FATAL BOUNDARY CHECK, `[SSOT Context]`, Мета, Кроки, Обмеження, Definition of Done з SSOT-пунктами, порожні Report і Verdict. Один підпроєкт = один файл; крос-проєктна фіча = файл на кожен підпроєкт із `related:`. ТЗ фіксує мету, межі та критерії приймання, не мікроменеджить реалізацію.
**5.2a Модель L1.** Кожен task-файл несе поле `model:` — рекомендацію Архітектора. Дефолт — `flash-3.8 high` (Gemini 3.8 Flash, thinking high). `pro-3.1` або `claude-opus` — лише як fallback: після двох REJECTED поспіль на тій самій задачі, при зацикленні L1, або для великих архітектурних рефакторингів. Gans бачить поле на етапі «ок» і може переграти; модель обирається ним у Antigravity перед `/task`. Поле `subagents: review | research | none` задає мінімум очікуваних від L1 read-only субагентів; кількість не обмежена — можливості L1 використовуються максимально. Дефолт — `review` (незалежне рев'ю перед Report для будь-якої задачі, документної теж); `research` — коли задача впирається в зовнішнє знання чи великий аудит (дослідження + рев'ю); `none` — лише за вказівкою Gans і означає **заборону** субагентів у задачі (не «мінімум 0»); тоді незалежне рев'ю робить Архітектор власним субагентом. L1 у Editor субагентів не має, тож `review`/`research` означає запуск в Agent Manager, воркспейс — завжди підпроєкт.

**5.3 Тригер.** Gans у Antigravity (воркспейс підпроєкту): `/task <ID>`.
**5.4 Верифікація (Zero Trust, Anti-Rush).** Report → `git -C <P> log --oneline -5`, `show --stat`, `diff` (великий diff — субагенту зі стислим звітом) → SSOT: пункт видалено з Plan, запис у Changelog, Context оновлено → `git status --short` чистий → Definition of Done по пунктах → `# Verdict` у файлі: VERIFIED / REJECTED + зауваження → статус. REJECTED → `status: pending`, Gans знову `/task <ID>`. VERIFIED без `hil_required` → `done`, файл у `tasks/done/`; з `hil_required` → чекати письмового PASS від Gans. Ніколи не казати Gans «готово» до п. VERIFIED. Ніколи не вірити Report без diff. Виконувані артефакти (`.ps1`, `.sh`, systemd-юніти, Makefile) перевіряти **парсингом або запуском**, не переглядом: `Parser::ParseFile` для PowerShell, `bash -n`, `systemd-analyze verify`. Дефекти кодування й байтових послідовностей при читанні коду невидимі в принципі. Заміри в Report приймаються лише з указанням процесу й коміту; контрольний замір Архітектора — після перезапуску сервісу або in-process, інакше він недійсний.
**5.5 Після done.** Крос-проєктне → `Global_Context.md`; закрито етап → `Global_Roadmap.md` + `Global_Changelog.md`. Етапи Plan не закриваються без підтвердження Gans.

## 6. Постійні протоколи Архітектора
- **Cross-Project Audit.** Баг/вразливість в одному підпроєкті → перевірити решту.
- **Stage Finalization.** Закриття етапу Roadmap лише після аудиту відповідної частини кодової бази (субагенти, пропорційно).
- **Аудит скілів Gemini.** Регулярно та після повторюваних Errors & Obstacles: застарілі шляхи, дублікати, відсутні guardrails → правити скіли, синтезувати нові правила з реальних помилок L1.
- **Онбординг підпроєкту.** Додати `[[projects]]` в `ecosystem.toml` → `python <kit>/sync.py` → заповнити `<P>/.agents/agents.local.md` і `project-rules.md` → рядок у `Global_Context.md` → перша задача L1: створити Holy Trinity.
- **Правки протоколу.** Усе, що є протоколом (шапка `AGENTS.md`, `/task`, шаблон задачі, глобальний `AGENTS.md` Gemini, цей файл окрім §2/§6), правиться ЛИШЕ в репозиторії `l2l1-kit` і розкочується `sync.py` на кожній машині; згенеровані файли мають маркер GENERATED і перезаписуються.
- **Ніщо не зроблено, поки не запушено.** Правка протоколу, скіла чи Global_* існує лише тоді, коли вона в `origin`. Локальна зміна + `sync.py` оновлюють ЦЮ машину; на іншій машині або в чистому клоні діятиме стара версія. Тому кожна зміна в `l2l1-kit` і в meta-репозиторії кореня завершується `git commit` + `git push` у ТІЙ САМІЙ відповіді, не «потім». `sync.py` наприкінці друкує список репозиторіїв із незапушеними комітами — якщо він щось вивів, робота не закінчена.
- **Мета-моніторинг.** Протокол «тре» → запропонувати Gans правку цього файлу або AGENTS.md L1.

## 7. Контекст-гігієна Claude
**SSOT перед кожним рішенням.** Будь-який висновок про підсистему починається з `grep` відповідного розділу `Context_<X>.md` і `Changelog_<X>.md`, і лише потім читається код. Це не разова дія бутстрапу, а передумова кожної змістовної відповіді: SSOT фіксує намір, застереження й історію рішень, яких у коді немає. Код читати з початку файлу, а не з середини. Розбіжність SSOT і коду — знахідка, про яку повідомляють Gans, а не привід мовчки довіритись коду; мовчання SSOT про важливе — привід запропонувати запис.

Не читати Context/Changelog цілком без потреби; великі diff-и й аудити — через субагентів; не вставляти в чат великі шматки коду.
